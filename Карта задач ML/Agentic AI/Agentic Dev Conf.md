# Канал 3 (Вебпрактик):
Трансформация *SDLC* (Software Development Life Cycle) — это структурированный процесс создания и поддержки программного обеспечения, который разбивает работу на последовательные этапы для контроля качества и сроков.

Spec-Driven Development (*SDD*) - подход, где спецификация становится единственным источником истины.

*AI-adoption* - процесс интеграции и регулярного использования инструментов ai в повседневные рабочие процессы разработчиков и команд.
Путь до 100% адопшн - парное программирование инженера с 95% разработчиков и их задачами
Остальные 5% добили кадровыми решениями

Матрица *зрелости* разработчика в AI:
L1 Решает задачи агентом, базовый промптинг (подписка младшая)
L2 Контекст, правила, ревью результата (подписка средняя)
L3 Харнесс, декомпозиция, проверки (выше средней)
L4 Системная работа с практиками (макс)

Бас-фактор» (*Bus factor*) — это критический показатель в управлении проектами, 
который определяет, сколько ключевых участников команды должен сбить автобус, 
чтобы проект полностью остановился или закрылся.
ИИ может быстро проанализировать сложный код ушедшего разработчика, составить 
по нему документацию и объяснить новой команде, как всё устроено

OpenSpec как «рельсы», которые не дают ИИ уйти в сторону, галлюцинировать или ломать ваш старый код, пишется на Gherkin, можно заменить.
Три главных принципа:
- **Структура важнее кода (Structure before code):** ИИ-агент не имеет права написать ни одной строчки рабочего кода, пока человек не утвердит изменения в спецификации. 
- **Изоляция дельты:** Вместо того чтобы скармливать ИИ огромные файлы документации всей системы, фреймворк изолирует текущее изменение в папке `changes/<change-id>/`. ИИ видит только точечную дельту («какие изменения внести в источник истины»). 
- **Управление контекстом:** Файлы в вашей структуре служат жесткими внешними «рельсами» для LLM. ИИ читает `proposal.md`, понимает бизнес-логику, сверяется с техническими ограничениями в `design.md` и строго следует чек-листу в `tasks.md`.

# Базовые артефакты openspec — структура папок (все генерируется агентами, мы ревьюим, вносим правки)
openspec/
├── specs/                   # ИСТОЧНИК ИСТИНЫ (domains), описание того, как система работает сейчас
│   └── <domain>/
│       └── spec.md
└── changes/                 # активные предложения, что и зачем меняем сейчас, логи изменений
    └── <change-id>/
        ├── proposal.md      # (Инициация) Бизнес приходит с гипотезой («Хотим добавить оплату через СБП»). Аналитик описывает требования
        ├── design.md        # (Проектирование) Архитектор смотрит на требования и пишет ADR («Используем шлюз банка Х, новые таблицы в БД такие-то»)
        ├── tasks.md         # (Реализация ) Команда декомпозирует задачу на чек-лист (настроить конфиги, написать API, покрыть тестами) и идет кодить
        └── specs/           # (Формализация) Разработчик и QA пишут новые сценарии в формате Gherkin (дельта specs)

OpenSpec решает главную проблему ИИ-кодинга — забивание контекста
Папка <change-id>, в которой в сжатом виде (всего в 4 файлах) лежит концентрированная суть вашей задачи. 
Если ИИ запутался, отправляем промпт:
    «Сбрось контекст. 
    Прочитай файлы в папке changes/<change-id>/. 
    Мы находимся на шаге 3 в tasks.md. 
    Продолжай реализацию строго по этой логике».
И модель мгновенно возвращается в идеальное рабочее состояние.

Можно сделать свой сервис просмотра и поиска **change**

Все ли делать через change?
- нет, правки которые не трогают спеки, запускаем обычными промптами 
- например передвинуть/покрасить кнопку
- баг по спеке (поведение уже описано в источнике истины, просто чиним код по него)

Технический change в котором нет спек, хранит только контекст решения.
- например рефакторинг, меняется поведение но не смысл
